# 공동 기획 (ENGINE · MANAGE)

> - 엔진 프로젝트(`NAON-SPAM-FILTER-ENGINE`)와 관리 프로젝트(`NAON-SPAM-FILTER-MANAGE`)가 **함께 지켜야 하는 결정**만 둔다.
> - 각 프로젝트 안의 결정은 각 저장소의 `CLAUDE.md`, 세부 명세는 `docs/FUNC_SPEC.md`에 있다.
> - 이 문서와 `FUNC_SPEC.md`가 어긋나면 이 문서가 우선이다.
> - 이 문서를 바꾸면 두 프로젝트가 모두 영향을 받는다.

## 1. 두 프로젝트

두 프로젝트는 소스·빌드·배포가 모두 따로다. 서로 맞물리는 곳은 **서버 DB**(3장)와 **엔진 API**(4장) 두 곳뿐이다.

| 프로젝트 | 맡는 일 | 배포 |
|---|---|---|
| ENGINE | 메일 수신(SMTP), 판정(Rspamd + 자체 판정), 격리, 전달 큐, James 전달, 엔진 API | 엔진 Docker 묶음 (엔진 + Rspamd + Valkey, compose 1개) |
| MANAGE | 관리자 로그인·권한 확인, 격리함 열람·해제·삭제 기록, 이력·통계 조회, 정책·규칙·허용/차단 목록 관리 | 관리 Docker 1개 (관리 백엔드 + 관리 화면) |

- 두 저장소는 같은 상위 폴더에 나란히 둔다. MANAGE는 `../NAON-SPAM-FILTER-ENGINE/docs/` 경로로 이 문서를 참조한다.

## 2. 전체 구조

```
외부 메일 → [엔진 Docker 묶음: 엔진 + Rspamd + Valkey] → James
                 │        ↑ 엔진 API (해제·원문·학습·상태)
                 │        │
                 ▼        │
             [ 서버 DB ] ◀─ [관리 Docker: 관리 백엔드(Spring Boot) + 관리 화면(Svelte)]
                                   ↑ 서버 Nginx ← 관리자
```

- 서버 DB와 서버 Nginx는 Docker 밖, 서버에 별도로 구성한다. 우리 산출물이 아니다.

## 3. 연결 ① 서버 DB

- 엔진과 관리 백엔드가 같은 서버 DB에 접속한다(`SPAMFILTER_DB_URL`).
  - 엔진 묶음과 관리 Docker에는 DB 컨테이너를 넣지 않는다.
- **데이터마다 쓰는 쪽은 하나다.** 상대가 쓰는 데이터는 읽기만 한다.

  | 데이터 | 쓰는 쪽 | 읽는 쪽 |
  |---|---|---|
  | 처리 이력 | 엔진 | 관리 백엔드 (이력·통계 조회) |
  | 격리 목록 | 엔진 | 관리 백엔드 (격리함 조회) |
  | 전달 상태 | 엔진 | - |
  | 학습 데이터 | 엔진 | - |
  | 정책 | 관리 백엔드 | 엔진 (처리 결정) |
  | 규칙 | 관리 백엔드 | 엔진 (판정) |
  | 허용/차단 목록 | 관리 백엔드 | 엔진 (즉시 판정) |
  | 관리자 계정 | 관리 백엔드 | - |
  | 열람·해제·삭제 기록 | 관리 백엔드 | - |

- 격리 메일 원문과 전달 큐 스풀은 DB가 아니라 **엔진 묶음 볼륨의 파일**이다. 관리 백엔드는 원문을 엔진 API로만 본다.
- 테이블 이름·구조는 아직 정하지 않았다. 정하면 이 장에 추가한다.

## 4. 연결 ② 엔진 API

- 엔진만 할 수 있는 일만 엔진 API로 제공한다.

  | 엔진 API | 내용 | 엔진만 할 수 있는 이유 |
  |---|---|---|
  | 격리 해제 | 격리 메일을 전달 큐로 넘겨 James에 전달 | 전달 큐가 엔진에 있음 |
  | 격리 원문 조회 | 격리 메일 원문·첨부 제공 | 원문 파일이 엔진 묶음 볼륨에 있음 |
  | 학습 반영 | Rspamd 학습 + 자체 학습 | Rspamd와 학습 로직이 엔진 묶음에 있음 |
  | 엔진 상태 | 엔진·Rspamd·Valkey 상태, 전달 큐 상태 | 엔진 묶음 안의 상태 |

- 엔진 API는 **관리 백엔드만 호출한다.**
  - 엔진 API 포트는 관리 Docker에서만 접근하게 네트워크로 제한하고, 외부에 공개하지 않는다.
  - 관리 백엔드는 `ENGINE_API_URL`로 엔진 API 주소를 받는다.
- 요청·응답 형식은 아직 정하지 않았다. 정하면 이 장에 추가한다.

## 5. 한쪽이 멈췄을 때

- **엔진이 멈췄을 때**
  - 된다: 관리 화면 로그인, 이력·격리 목록 조회, 정책·규칙 수정 (서버 DB만 쓰는 기능).
  - 엔진이 살아날 때까지 안 된다: 격리 해제, 원문 보기, 학습 반영 (엔진 API가 필요한 기능).
- **관리 Docker가 멈췄을 때**: 메일 수신·판정·전달은 계속된다. 정책·규칙은 마지막으로 저장된 값으로 판정한다.

## 6. 진행 단계

단계별 ENGINE·MANAGE 할 일과 완료 기준은 `FUNC_SPEC.md` 9장에 있다.

1. 메일을 받아 James로 넘기는 기본 통로 (판정 없음)
2. Rspamd 판정 연동 + 격리함
3. 자체 판정: 국내 스팸 규칙, 규칙 관리 화면, 기존 스팸스나이퍼 설정 이관
4. 학습 기능
5. 품질 검증
6. 시범 운영 (판정만 기록 → 정확도 확인 후 적용)
7. 운영 준비
