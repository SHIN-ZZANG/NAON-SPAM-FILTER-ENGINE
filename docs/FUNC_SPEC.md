> - 상태: 검토용 초안. 아직 개발 시작 전이다.

> - 이 문서는 개발자용 세부 기능 명세다. 확정된 결정의 요약은 다음에 있고, 이 문서와 어긋나면 그쪽이 우선이다.
>   - 두 프로젝트 공동 결정(서버 DB, 엔진 API 등): `docs/SHARED.md`
>   - 엔진 결정: ENGINE 저장소 `CLAUDE.md` / 관리 결정: MANAGE 저장소 `CLAUDE.md`
> - 환경변수 이름, 라이브러리 후보, 규칙 예시 등은 초안 단계의 예시다. 실제 값은 개발하면서 정한다.
> - 변경 배경과 요약은 `docs/Naon-Spam-Filter 초안.md`(기획 변경 안내)를 본다.

## 0. 설계 원칙

- **스팸필터 엔진이 James 앞단의 관문이다.**
  - 메일 수신, 판정 요청, 최종 처리 결정, 격리, 전달, 기록을 맡는다.
- **프로젝트는 엔진 프로젝트와 관리 프로젝트 둘로 나눈다.**
  - 엔진 프로젝트(`NAON-SPAM-FILTER-ENGINE`): 메일 수신(SMTP), 판정, 격리, 전달 큐, James 전달, 엔진 API.
  - 관리 프로젝트(`NAON-SPAM-FILTER-MANAGE`): 관리 백엔드(Spring Boot) + 관리 화면(Svelte).
  - 두 저장소는 같은 상위 폴더에 나란히 둔다.
- **배포는 엔진 Docker 묶음과 관리 Docker로 나눈다.**
  - 엔진 묶음: 스팸필터 엔진·Rspamd·Valkey 컨테이너 3개를 compose 하나로 함께 띄우고 함께 멈춘다.
  - 관리 Docker: 관리 백엔드와 관리 화면을 컨테이너 1개로 배포한다.
    - 관리 화면은 관리 백엔드 jar 안에 넣어 함께 제공한다.
  - 서버 Nginx(Docker 밖, 서버에 별도 구성)는 관리자 요청을 관리 Docker로 전달한다.
    - 서버 Nginx에는 화면 파일을 두지 않는다.
- **서버 DB(Docker 밖, 서버에 별도 구성)를 엔진과 관리 백엔드가 함께 쓴다.**
  - 데이터마다 쓰는 쪽은 하나다(3-9).
  - 격리 원문 파일과 전달 큐 스풀은 엔진 묶음 볼륨에 둔다.
- **엔진만 할 수 있는 일은 엔진 API로 한다.**
  - 격리 해제, 격리 원문 조회, 학습 반영, 엔진 상태.
  - 엔진 API는 관리 백엔드만 호출한다.
- **엔진과 관리는 서로 멈춰도 각자 할 일을 계속한다.**
  - 엔진이 멈춰도 관리 화면에서 로그인, 이력·격리 목록 조회, 정책·규칙 수정은 된다.
  - 관리 Docker를 다시 배포하거나 멈춰도 메일 처리는 계속된다.
- **판정 기반은 Rspamd, 국내 스팸 대응은 자체 엔진.**
  - 두 점수를 합쳐 우리 정책으로 최종 결정한다.
  - Rspamd의 자체 처리 기준(action)은 쓰지 않는다.
- **스팸 판정으로는 거절하지 않고 격리한다.**
  - SMTP 단계 거절은 받을 수 없는 메일(우리 도메인 아님, 없는 사용자, 크기 초과)만.
- **"받았다(250)"고 응답한 메일은 잃지 않는다.**
  - 디스크 저장 후 응답한다.
- **품질의 신뢰성과 유지보수 용이성을 우선한다.**
  - 범용 판정은 검증된 Rspamd에 맡기고, 우리 코드는 국내 스팸 규칙·정책·격리·전달에 집중한다.

### 1-2. 판정별 처리 (초기값, 정책 화면에서 변경)

| 판정 | 조건 | 처리 |
|---|---|---|
| 격리 | 합산 15점↑, 차단 목록, 위험 첨부, 바이러스 | 엔진 격리함에 보관.<br>James로 보내지 않음 |
| 제목 태그 | 10~15점 | 제목에 `[SPAM]` + `X-Spam: Yes` 헤더 → James (Spam 폴더) |
| Spam 폴더 | 6~10점 | `X-Spam: Yes` 헤더 → James (Spam 폴더) |
| 정상 | 6점 미만, 허용 목록 | James로 전달 |

### 1-3. SMTP 단계별 처리

| 단계 | 확인 | 실패 시 |
|---|---|---|
| 접속 | 동시 접속 수, IP별 접속 수 | `4xx` |
| `EHLO` / `STARTTLS` | TLS 제공 | - |
| `MAIL FROM` | 기록 | - |
| `RCPT TO` | 우리 도메인인지, 실제 사용자인지 | `5xx` |
| `DATA` | 크기 제한 | `5xx` |
| 판정 | 본문 수신 완료 → Rspamd + 자체 엔진 | 오류 시 정책(2-5) |
| 응답 | 격리함 또는 전달 큐에 디스크 저장 완료 후 | `250` |
| 전달 | 전달 큐 → James SMTP, 실패 시 재시도 | - |

### 1-4. 운영 구성 (엔진 묶음 + 관리 Docker + 서버 Nginx + 서버 DB + James)

| 묶음 | 구성 요소 | 역할 | 외부 공개 |
|---|---|---|---|
| 엔진 묶음 (ENGINE) | 스팸필터 엔진 | 수신, 판정 결정, 격리, 전달, 엔진 API(격리 해제·원문 조회·학습 반영·상태).<br>스풀·격리 원문 보관(엔진 묶음 볼륨).<br>이력·격리 목록·전달 상태·학습 데이터는 서버 DB에 저장 | SMTP 25(개발 2525).<br>엔진 API는 관리 백엔드만 접근 (3-9) |
| 엔진 묶음 (ENGINE) | Rspamd | 범용 판정 (검사 11333, 관리 11334) | **공개하지 않음** (스팸필터 엔진·James만 접근) |
| 엔진 묶음 (ENGINE) | Valkey | Rspamd 데이터 저장 (Redis 호환) | 공개하지 않음 |
| 엔진 묶음 (선택 시 추가) | ClamAV | 바이러스 검사 (Rspamd가 호출) | 공개하지 않음 |
| 관리 Docker (MANAGE) | 관리 백엔드 + 관리 화면 | 관리자 로그인, 권한 확인, 격리함 열람·해제·삭제 기록, 이력·통계 조회, 정책·규칙·허용/차단 목록 관리.<br>엔진만 할 수 있는 일은 엔진 API 호출.<br>관리 화면은 관리 백엔드 jar 안에 넣어 함께 제공 | 서버 Nginx만 접근 |
| 서버 Nginx (Docker 밖, 별도 구성) | Nginx | 관리자 요청을 관리 Docker로 전달.<br>화면 파일은 두지 않음 | 관리자만 접근 |
| 서버 DB (Docker 밖, 별도 구성) | DB | 엔진과 관리 백엔드가 함께 사용.<br>데이터마다 쓰는 쪽은 하나 (3-9) | 공개하지 않음 (스팸필터 엔진·관리 백엔드만 접속) |
| 묶음 밖 | James | 메일함 | SMTP는 스팸필터 엔진 IP만 허용 |

- 엔진 묶음의 컨테이너 3개는 함께 띄우고 함께 멈춘다.
  - Rspamd·Valkey는 공식 이미지를 버전 태그로 고정해 그대로 쓴다.
  - 각 컨테이너는 Docker가 각자 자동 재시작한다.
- 관리 Docker는 엔진 묶음과 따로 띄우고 따로 멈춘다.
  - Docker가 자동 재시작한다.

- Rspamd에는 **Redis가 반드시 필요하다.**
  - Rspamd의 학습(베이지안), 신경망 분류, 평판, 처리 이력, 발송량 제한 기능이 Redis를 사용한다.
  - 없으면 이 기능들이 꺼지므로 Rspamd 표준 구성대로 함께 둔다.
- 그 자리에 Redis와 호환되는 오픈소스 저장소인 Valkey를 쓴다(Redis를 그대로 써도 된다).
- 스팸필터 엔진과 관리 백엔드의 데이터는 Redis가 아니라 서버 DB에 저장한다(3-9).

## 2. 판정

### 2-1. 판정 흐름

```
메일 + SMTP 정보(발신 IP, HELO, 발신자, 수신자)
   │
   ├─ 즉시 판정 (자체 엔진)  허용/차단 목록 ── 차단 → 격리 / 허용 → 정상(첨부·바이러스 검사는 계속)
   ├─ Rspamd /checkv2      ── 점수 + 걸린 심볼 (+ CLAM_VIRUS, 위험 첨부 심볼)
   ├─ 자체 엔진             ── 국내 스팸 규칙 점수 + 학습 점수 + 걸린 규칙
   ▼
합산 점수 + 걸린 규칙(Rspamd 심볼 + 자체 규칙) ──▶ 정책으로 처리 결정
```

- 바이러스(`CLAM_VIRUS`)와 위험 첨부는 점수와 관계없이 격리한다.
  - 허용 목록이어도 건너뛰지 않는다(발신자 위조 대비).
- 허용/차단 목록은 관리 백엔드가 서버 DB에 저장하고, 자체 엔진이 서버 DB에서 읽어 직접 판정한다.
  - 허용/차단 목록은 Rspamd에 넘기지 않는다.
- 점수 정책도 관리 백엔드가 서버 DB에 저장하고, 엔진이 읽어 처리 결정에 쓴다.

### 2-2. Rspamd 호출

- `DATA` 수신 후 `/checkv2`에 원문을 보내고, SMTP 대화 정보를 HTTP 헤더로 함께 넘긴다.
  - 빠뜨리면 SPF·평판 검사가 제대로 안 된다.

  | 헤더 | 값 |
  |---|---|
  | `IP` | 보낸 서버 IP |
  | `Helo` | EHLO 이름 |
  | `From` | MAIL FROM |
  | `Rcpt` | RCPT TO (수신자마다) |
  | `Queue-Id` | 스팸필터 엔진이 붙인 메일 ID |

- 응답에서 `score`와 `symbols`만 쓴다.
  - `action`은 무시하고 처리는 우리 정책으로 정한다.
  - 따라서 점수 정책 변경을 Rspamd에 반영(`/saveactions`)할 필요가 없다.
- Rspamd 심볼의 한글 설명은 관리 화면에서 이력·대시보드를 보여 줄 때 쓴다(7-2).
- 호출 시간 제한을 둔다.
  - 초과·오류 시 처리는 2-5.

### 2-3. 자체 엔진 (국내 스팸 규칙)

- 규칙은 **서버 DB에 저장하고 관리 화면에서 추가·수정·끄기**를 한다.
  - 규칙 저장은 관리 백엔드가, 규칙 실행은 엔진이 맡는다.
  - 엔진은 재시작 없이 바뀐 규칙을 반영한다.
- 규칙 항목: 코드, 한글 이름, 대상(제목 / 본문 / 헤더 / URL / 첨부 이름), 조건(키워드 / 정규식), 점수, 사용 여부, 설명, 수정자·수정 시각.
- **규칙 시험**: 메일 원문을 넣어 어떤 규칙이 걸리는지 미리 보고, 저장 전 최근 메일에 돌려 몇 건이 걸리는지 보여 준다.
- 정규식은 처리 시간이 폭증하지 않는 엔진(RE2J 등 선형 시간)으로 실행한다.
- 변경 이력(누가, 언제, 무엇을)을 남긴다.

**국내 스팸 규칙 초기 세트 예시**

| 규칙 | 근거·내용 |
|---|---|
| 광고 표기 위반 | 정보통신망법상 광고성 메일은 제목에 "(광고)"를 표시해야 함.<br>광고성 문구가 있는데 표기가 없으면 가점 |
| 수신거부 안내 누락 | 광고성 메일인데 수신거부 방법 안내가 없음 |
| 대출·도박·성인 문구 | 국내 스팸 상투 문구, 변형 표기(띄어쓰기·특수문자 끼움) 포함 |
| 기관·금융 사칭 | 표시 이름에 국세청·은행·택배사 등 + 발신 도메인 불일치 |
| 단축 URL 다수 | 단축 URL·무료 호스팅 링크 비중이 높음 |
| 제목 인코딩 위장 | 필터 회피용 인코딩·특수문자 남용 |

### 2-4. 학습

| 학습 | 담당 | 신호 |
|---|---|---|
| Rspamd 학습 (범용) | Rspamd (Valkey에 저장) | 사용자 Spam 폴더 이동 → James `RspamdListener`가 Rspamd에 직접 학습 (3-8).<br>관리자 격리 해제·"스팸으로 학습" → 관리 백엔드가 엔진 API(학습 반영) 호출 → 스팸필터 엔진이 Rspamd `/learnham`·`/learnspam` 호출 |
| 한국어 학습 (자체 엔진) | 스팸필터 엔진 (서버 DB) | 관리자 격리 해제·"스팸으로 학습" (엔진 API 학습 반영).<br>사용자 Spam 폴더 이동까지 쓰려면 James 리스너 확장(작은 jar)이 추가로 필요 (10장 결정) |

- 학습 데이터는 엔진이 서버 DB에 쓴다.
- 한국어 학습은 형태소 분석(Lucene Nori, 엔진 안에서 동작)으로 낱말을 쪼갠다.
  - Rspamd 기본 학습은 한국어 형태소를 고려하지 않는다.
- 최소 학습량(예: 스팸·정상 각 200통)을 넘기 전에는 자체 학습 점수를 반영하지 않는다.
- 엔진 자기 판정으로는 학습하지 않는다(오판이 굳어짐).
  - 사람의 판단만 쓴다.

### 2-5. 장애 처리

- **Rspamd 오류·시간 초과**
  - 정책으로 정한다.
  - `4xx`로 미루기(권장. 보낸 쪽이 재시도) / 자체 엔진 점수만으로 판정 / 일단 격리.
- **ClamAV 다운**
  - Rspamd는 바이러스 검사 없이 판정을 계속한다.
  - 상태 화면과 알림으로 알린다.
- 판정 단계별 처리 시간을 기록한다.

### 2-6. 품질 검증

- **평가 데이터**
  - 스팸·정상 메일 표본으로 규칙 변경·Rspamd 업그레이드 때마다 탐지율과 오탐률을 잰다.
  - 오탐을 더 무겁게 본다.
- **시범 운영**
  - 실제 메일에 판정만 붙여 기록하고 처리는 하지 않는다.
  - 오탐이 충분히 낮아진 뒤 격리를 켠다.

## 3. 게이트웨이

### 3-1. SMTP 수신

- Spring Boot 앱 안에 SMTP 서버 라이브러리를 내장한다.
  - 후보: SubEthaSMTP(유지보수 중인 fork), Apache James protocols(Netty 기반).
  - 1단계 PoC에서 정한다.
- 개발 환경에서는 2525 포트.
  - 포트·바인딩 주소, 접속 제한, 메시지 최대 크기, 타임아웃은 환경변수.
- STARTTLS 인증서는 설정 경로에서 읽는다.
  - 개발 환경에서는 없이 동작.
- 외부에서 들어온 `X-Spam*` 헤더는 지우고 우리 판정 결과만 붙인다.

### 3-2. 받는 사람 검증 (오픈 릴레이 방지)

- 우리 도메인이 아닌 수신자는 무조건 거절한다.
  - 빠지면 남의 스팸을 대신 보내 주는 오픈 릴레이가 된다.
- 없는 사용자는 `RCPT TO`에서 거절한다(받은 뒤 반송하면 가짜 발신자에게 반송 메일을 뿌리게 됨).
- 도메인·사용자 목록은 James WebAdmin(`/domains`, `/users`)에서 주기적으로 가져와 캐시한다.
  - James가 응답하지 않으면 마지막 캐시로 판단한다.

### 3-3. 수신자가 여럿일 때

- 1단계: 수신자 전체에 같은 판정.
  - 허용/차단 목록은 전체(GLOBAL) 기준.
- 판정이 받은 뒤의 처리이므로, 수신자별 정책(`RuleScope.DOMAIN/USER`)을 붙일 때 수신자마다 다르게 처리할 수 있다(2단계 과제).

### 3-4. 전달 큐

- `250` 전에 원문을 스풀 디렉터리에 저장하고 저장 완료를 확인한다.
  - 상태는 서버 DB(`delivery_queue`: 메일 ID, 수신자, 상태, 시도 횟수, 다음 시도 시각, 마지막 오류).
  - 전달 상태는 엔진이 쓴다.
- James로 SMTP 전달(Jakarta Mail, 이미 의존성에 있음):
  - 성공 → 큐에서 제거, 이력에 기록
  - 일시 오류(`4xx`, 연결 실패) → 간격을 늘려 재시도
  - 영구 거절(`5xx`) → 실패 표시, 관리 화면 알림 (발신자 반송 여부는 10장)
  - 정해진 기간(예: 3일) 넘게 실패 → 실패 표시, 알림
- 관리 화면: 큐 길이, 오래 머문 메일.
  - 관리 백엔드가 엔진 API(엔진 상태)로 받아 보여 준다.

### 3-5. 격리함

- 원문은 파일(엔진 묶음 볼륨), 격리 목록(시각, 발신자, 수신자, 발신 IP, 제목, 점수, 걸린 규칙, 격리 사유, 크기, 파일 경로)은 서버 DB.
  - 원문 파일과 격리 목록은 엔진이 쓴다.

  | 격리 사유 | 해제 | 원문·첨부 다운로드 |
  |---|---|---|
  | 스팸 점수 | 가능 | 가능 |
  | 차단 목록 | 가능 (확인 창) | 가능 |
  | 위험 첨부 | 확인 창 후 가능 (10장 결정) | 차단 또는 암호 압축 |
  | 바이러스 | 불가 | 차단 |

- 격리 목록 조회는 관리 백엔드가 서버 DB에서 직접 읽는다.
  - 엔진이 멈춰도 목록은 볼 수 있다.
- 원문 보기·다운로드는 원문 파일이 엔진 쪽에 있으므로 관리 백엔드가 엔진 API(격리 원문 조회)로 가져온다.
- 해제 → 관리 백엔드가 엔진 API(격리 해제)를 호출하고, 엔진이 전달 큐로 James에 보낸다.
  - 재검사는 하지 않는다.
  - 해제는 정상 학습 신호로 쓴다(2-4).
- 열람 권한을 제한하고, 열람·해제·삭제 기록을 남긴다.
  - 권한 확인과 기록은 관리 백엔드가 처리한다(3-9).
- 보관 기간이 지나면 자동 삭제한다.
  - 필요하면 사유·점수별로 다르게.
- 격리 저장 경로를 서버 백신 실시간 검사에서 제외할지 정한다(제외하지 않으면 백신이 파일을 지워 보관이 깨짐).
- 격리는 엔진 격리함에서만 한다. James에는 격리 저장소를 두지 않는다.

### 3-6. 왜 거절하지 않고 격리하는가

- 거절(SMTP `5xx`)은 보낸 쪽이 반송 안내를 받는다는 점 말고는, 원문 보관이 필요한 이상 격리와 실질 차이가 없다.
- 격리로 통일하면 오탐도 해제로 구제할 수 있고, 보관함이 하나라 관리가 단순하다.
- 보낸 사람은 스팸 분류 사실을 모르므로, 사용자별 격리 알림(예: 하루 한 번 "격리된 메일 N건")을 2단계 과제로 둔다.

### 3-7. 가용성 (운영 단계)

- 엔진 묶음이 멈추면 수신이 멈춘다.
  - 보낸 쪽 재시도로 짧은 중단은 지연으로 끝난다.
- 운영 선택지: 엔진 묶음 2대 + MX 2개, 또는 L4 부하분산.
  - 2대면 두 엔진이 같은 서버 DB를 쓴다.
  - 스풀·격리함 저장소의 공유 방식을 정한다.
- 관리 Docker는 엔진 묶음과 따로 배포한다.
  - 관리 Docker를 다시 배포하거나 멈춰도, 서버 Nginx가 멈춰도 메일 수신·판정·전달은 계속된다.
  - 서버 Nginx와 관리 Docker는 메일 처리 경로에 없으므로 이중화 대상에 넣지 않는다.

**엔진이 멈췄을 때**

- 관리 화면에서 되는 것 (관리 백엔드와 서버 DB로 처리)
  - 관리자 로그인
  - 처리 이력·통계 조회, 격리 목록 조회
  - 정책·규칙·허용/차단 목록 수정 (엔진이 다시 살아나면 서버 DB에서 읽어 반영)
- 엔진이 살아날 때까지 안 되는 것 (엔진 API가 필요)
  - 격리 해제
  - 격리 원문 보기
  - 학습 반영
- 대응
  - **자동 재시작**: 엔진 묶음의 컨테이너마다 Docker 재시작 정책(`restart`)을 둔다.
  - **메일 보존**: `250`으로 받은 메일은 전달 큐(디스크)에 남아 있어 재시작 후 이어서 전달한다.
    - 아직 받지 못한 메일은 보낸 쪽 서버가 재시도한다.
  - **화면 표시**: 엔진 API가 응답하지 않으면 관리 화면에 "엔진 응답 없음"을 분명히 표시하고, 엔진이 필요한 기능(해제·원문 보기·학습)을 막는다.
    - 엔진 상태가 정상으로 오해되지 않게 한다.
  - **외부 감시**: 엔진 상태(헬스 체크, SMTP 포트 응답)를 관리 화면에 의존하지 않는 외부 감시로 확인하고 담당자에게 알린다.
    - 감시 수단(사내 모니터링 등)은 운영 준비 단계에서 정한다.
  - **이중화**: 운영 단계에서는 위 엔진 묶음 이중화로 중단 자체를 줄인다.

### 3-8. James 쪽 변경

- `mailetcontainer.xml`
  - James는 판정하지 않는다. Rspamd 검사(`RspamdScanner`)와 격리 저장소를 두지 않는다.
  - Spam 폴더 분류: 엔진이 붙인 `X-Spam` 헤더 기준 매처(예: `HasHeaderWithValue=X-Spam,Yes`)로 Spam 폴더에 넣는다.
    - 매처 이름은 버전별 확인
- `listeners.xml`(`RspamdListener`), `rspamd.properties`: 사용자 Spam 폴더 이동 → Rspamd 학습
- James는 스팸필터 엔진을 거친 메일만 받도록 제한한다.
  - James가 어느 네트워크에 있든, 인터넷 메일을 직접 받는 SMTP 수신은 막고 스팸필터 엔진 IP의 연결만 허용한다.
- MX 레코드는 스팸필터 엔진을 가리키게 바꾼다.

### 3-9. 관리 프로젝트 ↔ 엔진 연결

**엔진 API 범위**

- 엔진만 할 수 있는 일만 엔진 API로 제공한다.

  | 엔진 API | 내용 | 엔진만 할 수 있는 이유 |
  |---|---|---|
  | 격리 해제 | 격리 메일을 전달 큐로 넘겨 James에 전달 | 전달 큐가 엔진에 있음 |
  | 격리 원문 조회 | 격리 메일 원문·첨부 제공 (사유별 제한은 3-5) | 원문 파일이 엔진 묶음 볼륨에 있음 |
  | 학습 반영 | Rspamd 학습 + 자체(한국어) 학습 | Rspamd와 학습 로직이 엔진 묶음에 있음 |
  | 엔진 상태 | 엔진·Rspamd·Valkey·(선택) ClamAV 상태, 전달 큐 상태 | 엔진 묶음 안의 상태 |

- 엔진 API는 관리 백엔드만 호출한다.
  - 엔진 API는 관리 Docker에서만 접근하게 네트워크로 제한한다.
  - 인터넷에는 SMTP 포트만 공개하고, 엔진 API 포트는 공개하지 않는다.

**관리 백엔드 역할**

- 관리 백엔드(Spring Boot)가 관리 API를 제공하고, 관리 화면은 이것만 호출한다.
  - 관리 화면(Svelte)은 관리 백엔드 jar 안에 넣어 관리 Docker 하나로 함께 제공한다.
- 관리 백엔드가 맡는 일
  - 관리자 로그인, 권한 확인
  - 격리함 열람·해제·삭제 기록, 설정 변경 기록
  - 처리 이력·통계 조회, 격리 목록 조회
  - 정책·규칙·허용/차단 목록 관리
  - 엔진만 할 수 있는 일(3-9 엔진 API 범위)은 엔진 API 호출
- 관리자 계정
  - 관리 화면은 **스팸필터 전용 관리자 계정**으로 로그인한다.
  - 계정은 서버 DB에 두고, 로그인은 관리 백엔드가 처리한다.
- 접근 제한
  - 서버 Nginx는 우리가 만드는 산출물이 아니라, 서버에 별도로 구성하는 것이다(Docker 밖).
  - 서버 Nginx는 관리자 요청을 관리 Docker로 전달하고, 관리자만 접근하게 제한한다.
    - 화면 파일은 서버 Nginx에 두지 않는다.
  - 관리 Docker는 서버 Nginx에서만 접근하게 네트워크로 제한한다.
  - 네트워크 제한과 별개로, 모든 관리 API는 로그인한 관리자의 권한을 확인한다.

**서버 DB 공유 원칙**

- 서버에 별도로 구성한 DB(Docker 밖)에 엔진과 관리 백엔드가 함께 접속한다(`SPAMFILTER_DB_URL`).
  - 서버 DB는 우리 산출물이 아니라 서버에 별도로 구성하는 것이다.
  - 엔진 묶음과 관리 Docker에는 DB 컨테이너를 넣지 않는다.
- 데이터마다 쓰는 쪽은 하나다.

  | 데이터 | 쓰는 쪽 | 읽는 쪽 |
  |---|---|---|
  | 처리 이력 | 엔진 | 관리 백엔드 (이력·통계 조회) |
  | 격리 목록 | 엔진 | 관리 백엔드 (격리함 조회) |
  | 전달 상태 | 엔진 | - |
  | 학습 데이터 | 엔진 | - |
  | 정책 | 관리 백엔드 | 엔진 (처리 결정) |
  | 규칙 | 관리 백엔드 | 엔진 (판정) |
  | 허용/차단 목록 | 관리 백엔드 | 엔진 (즉시 판정) |
  | 관리자 계정 | 관리 백엔드 | - |
  | 열람·해제·삭제 기록 | 관리 백엔드 | - |

- 격리 원문과 전달 큐 스풀은 파일로 엔진 묶음 볼륨에 둔다.

**엔진이 멈췄을 때**

- 관리 화면에서 로그인, 이력·격리 목록 조회, 정책·규칙 수정은 된다.
- 격리 해제·원문 보기·학습 반영은 엔진이 살아날 때까지 안 된다.
- 대응은 3-7 "엔진이 멈췄을 때".

| 단계 | 방법 | 추가 구성 |
|---|---|---|

## 5. Rspamd 운영

- **이미지 버전 고정**: `rspamd/rspamd:latest`를 쓰지 않고 검증한 버전 태그로 고정한다.
- **설정 관리**
  - ENGINE 저장소에서 관리한다. 개발 시작 때 엔진 묶음 구성과 함께 만든다.
  - 원본 설정은 건드리지 않고 바꿀 부분만 `local.d`에 적는다.
- **업그레이드 절차**
  - 검증 환경에서 새 버전으로 평가 데이터를 돌려 판정 변화를 확인 → 이상 없으면 운영 반영.
  - 주기는 10장에서 정한다.
- **보안**
  - 11333/11334는 외부에 공개하지 않는다.
  - 관리 비밀번호는 `rspamadm pw`로 만든 해시를 쓴다.
- **Valkey**: 데이터를 볼륨에 저장해 재시작해도 학습 데이터가 남게 한다.
- **상태 감시**: 엔진 API(엔진 상태)에 Rspamd·Valkey·(선택) ClamAV 상태를 넣고, 관리 화면 상태 표시에 보여 준다.
- **라이선스**
  - Rspamd는 Apache 2.0.
  - 제품에 포함해 배포할 때 라이선스 고지를 넣는다.
- **설정 원칙**
  - Rspamd의 처리 기준(action)은 판정에 쓰지 않는다. 기준값을 Rspamd 설정에 두지 않는다.
  - 허용/차단 목록은 Rspamd에 두지 않는다(엔진이 서버 DB에서 읽어 판정, 2-1).
  - 처리 이력은 엔진이 서버 DB에 기록한다. Rspamd 이력(`history_redis`)은 Rspamd 웹 화면 확인용으로 최소한만.

## 6. 스팸스나이퍼 활용 범위

| 구분 | 항목 | 활용 |
|---|---|---|
| 가져와도 됨 | 우리가 등록한 허용/차단 목록, 우리가 추가한 규칙, 우리가 정한 기준값, 도메인·사용자별 설정 | 이관.<br>공식 내보내기 기능 우선 |

## 7. 코드 영향

- ENGINE과 MANAGE는 별개 프로젝트로 각자 만든다. 코드를 공유하지 않고, 서버 DB와 엔진 API(`docs/SHARED.md`)로만 연결한다.
- Rspamd는 엔진만 호출한다. 관리 백엔드는 Rspamd·James를 직접 호출하지 않는다.

### 7-1. ENGINE 프로젝트

| 항목 | 조치 |
|---|---|
| 신규: SMTP 수신 (`smtp/`) | SMTP 서버, 수신자 검증, 판정 호출, 처리 분기 |
| 신규: 자체 엔진 (`engine/`) | 즉시 판정(허용/차단·위험 첨부), 국내 스팸 규칙 엔진, 점수 합산.<br>정책·규칙·허용/차단 목록은 서버 DB에서 읽어 재시작 없이 반영 |
| 신규: 한국어 학습 | 토큰 테이블, 학습·판정 로직 |
| 신규: 전달 큐 | 스풀, `delivery_queue`, 재시도 스케줄러, James SMTP 전달 |
| 신규: 수신자 캐시 | James WebAdmin에서 도메인·사용자 목록 주기 갱신 |
| 신규: 격리함 저장 | 원문 파일(엔진 묶음 볼륨) + 격리 목록(서버 DB).<br>보관 기간 자동 삭제 스케줄러 |
| 신규: 처리 이력 기록 | 판정 시점에 서버 DB에 직접 기록.<br>처리 결과, 격리 사유, 발신 IP, Rspamd 점수·자체 점수, 걸린 규칙, 전달 상태, 원문 위치 |
| 신규: 엔진 API | 격리 해제(→전달 큐), 격리 원문 조회, 학습 반영(Rspamd 학습 + 자체 학습), 엔진 상태.<br>관리 백엔드만 호출 |
| 신규: Rspamd 연동 | `/checkv2` 호출(SMTP 정보 IP·HELO·발신자·수신자 포함, 2-2), `/learnspam`·`/learnham` 호출, 상태 확인.<br>시험용 mock 구현 |
| 신규: 엔진 묶음 배포 | 엔진 묶음 docker-compose(엔진 + Rspamd + Valkey)와 Rspamd 설정 (5장, 8-2) |

### 7-2. MANAGE 프로젝트

| 항목 | 조치 |
|---|---|
| 관리 백엔드 | Spring Boot. 관리 API, 서버 DB(`SPAMFILTER_DB_URL`) 연결 |
| 관리 화면 | Svelte. 로그인 화면 포함.<br>엔진 API가 응답하지 않으면 "엔진 응답 없음" 표시, 엔진이 필요한 기능(해제·원문 보기·학습) 막음 |
| 배포 | 관리 화면 빌드 결과를 관리 백엔드 jar 안에 넣어 관리 Docker 이미지 1개로 배포.<br>서버 Nginx가 관리자 요청을 관리 Docker로 전달 |
| 관리자 계정·로그인 | 스팸필터 전용 관리자 계정, 로그인 API, 권한 확인 |
| 열람 기록 | 격리함 열람·해제·삭제 기록, 설정 변경 기록 |
| 엔진 API 호출 | 격리 해제, 격리 원문 조회, 학습 반영, 엔진 상태 |
| 격리함 | 격리 목록은 서버 DB에서 읽고, 해제·원문은 엔진 API 호출.<br>사유별 해제 제한, 열람·해제·삭제 기록 |
| 처리 이력 조회 | 엔진이 서버 DB에 기록한 처리 이력을 읽어 조회 |
| 점수 정책 | 3단계(격리 / 제목 태그 / Spam 폴더) 기준값을 서버 DB에 저장. 엔진이 읽어 반영 |
| 허용/차단 목록 | 서버 DB에 저장. 엔진이 읽어 판정 |
| 규칙 관리 | 규칙 테이블, 관리 API·화면, 규칙 시험, 변경 이력 |
| Rspamd 심볼 한글 설명 | 이력·대시보드에 Rspamd 심볼을 한글로 표시.<br>자체 규칙은 규칙 테이블의 한글 이름 사용 |
| 대시보드 / 상태 화면 | 격리 사유별 건수, 많이 걸린 규칙(Rspamd + 자체) / 엔진 상태(SMTP 수신, 전달 큐, James 전달, Rspamd·Valkey·(선택) ClamAV) |
| 전달 큐 상태 화면 | 엔진 상태 API로 조회 |
| mock 모드 | 엔진 API mock 구현, 샘플 격리·이력·규칙 데이터 |

## 8. 설정·구성 변경

### 8-1. 환경변수

**ENGINE (엔진 묶음)**

| 변수 | 설명 |
|---|---|
| `SMTP_PORT`, `SMTP_HOST` | SMTP 수신 포트·바인딩 주소 (개발 2525, 운영 25) |
| `SMTP_MAX_CONNECTIONS`, `SMTP_MAX_CONNECTIONS_PER_IP` | 접속 제한 |
| `SMTP_MAX_MESSAGE_SIZE` | 메시지 최대 크기 (James와 같게) |
| `SMTP_TLS_CERT`, `SMTP_TLS_KEY` | STARTTLS 인증서 |
| `JAMES_SMTP_HOST`, `JAMES_SMTP_PORT` | James 전달 주소 |
| `SPOOL_PATH`, `QUARANTINE_STORE_PATH` | 전달 큐·격리함 원문 경로 |
| `RSPAMD_NORMAL_URL`, `RSPAMD_CONTROLLER_URL`, `RSPAMD_PASSWORD` | Rspamd 검사·관리 API 주소, 관리 비밀번호 |
| `RSPAMD_TIMEOUT_MS`, `JUDGE_FAILURE_MODE` | Rspamd 호출 시간 제한, 오류 시 `tempfail` / `local-only` / `quarantine` |
| `SPAMFILTER_DB_URL` | 서버 DB 접속 정보 |

**MANAGE (관리 Docker)**

| 변수 | 설명 |
|---|---|
| `SPAMFILTER_DB_URL` | 서버 DB 접속 정보 |
| `ENGINE_API_URL` | 엔진 API 주소 |

- 서버 Nginx가 관리 Docker로 전달할 주소는 서버 Nginx 설정에서 지정한다.
- 관리 Docker는 Rspamd·James에 접속하지 않으므로 그 접속 정보를 두지 않는다.

### 8-2. docker-compose

- **엔진 묶음**: ENGINE 저장소에 둔다(개발 시작 때 만든다)
  - 컨테이너 3개를 함께 띄우고 함께 멈춘다.
  - 엔진(스팸필터 엔진): SMTP 포트 공개(개발 2525).
    - 엔진 API 포트는 관리 Docker에서만 접근하게 연다(3-9).
  - `rspamd`: 공식 이미지, 버전 태그 고정, 11333/11334는 외부에 공개하지 않음
  - `valkey`: 공식 이미지, 버전 태그 고정
  - 컨테이너마다 자동 재시작(`restart`)을 둔다.
  - DB 컨테이너는 없다(서버 DB에 접속, 3-9).
  - 볼륨: 전달 큐 스풀, 격리 원문, Valkey 데이터
  - (선택) `clamav`: 4장 결정 시 추가
- **관리 Docker**: MANAGE 저장소
  - 컨테이너 1개(관리 백엔드 + 관리 화면).
  - 포트는 서버 Nginx에서만 접근하게 연다(3-9).
  - 자동 재시작(`restart`)을 둔다.
  - DB 컨테이너는 없다(서버 DB에 접속, 3-9).
  - 엔진 묶음과 따로 띄우고 따로 멈춘다.
- 서버 Nginx와 서버 DB는 compose에 넣지 않는다.
  - 둘 다 Docker 밖에서 서버에 별도로 구성한다(3-9).

## 10. 결정 필요 사항

1. 점수 경계: 격리 / 제목 태그 / Spam 폴더 (초기값 15 / 10 / 6)
2. Rspamd 오류 시: `4xx`로 미루기(권장) / 자체 엔진 점수만으로 판정 / 일단 격리
3. 바이러스 검사: 위험 첨부 격리만 / + ClamAV / + 사내 백신.
   - 위험 첨부 확장자 목록과 해제 허용 여부
4. 평판 목록 사용 조건: Rspamd가 쓰는 공개 목록(Spamhaus 등)의 상용 계약 여부, 조회용 DNS 리졸버
5. 한국어 학습에 사용자 신호도 쓸지 (James 리스너 확장 개발 여부)
6. 격리함 보관 기간(일괄 / 사유·점수별), 열람 권한자, 열람 기록 보관 기간
7. James 영구 거절 시 발신자 반송 여부
8. SMTP 라이브러리 (1단계 PoC에서 결정)
9. 운영 James 버전 (매처 이름 확인용)
10. Rspamd 버전 업그레이드 주기와 검증 절차
11. 발신 메일(사내 → 외부)도 거칠지 (이 문서는 수신만)
12. 운영 이중화 방식
13. 스팸스나이퍼 사용권 계약 확인 결과와 이관 범위
14. 서버 DB 구조(스키마) 변경을 어느 프로젝트가 관리할지
